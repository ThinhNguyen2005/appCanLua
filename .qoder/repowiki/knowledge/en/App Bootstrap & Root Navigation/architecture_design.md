Two top-level components form the app's bootstrap boundary:
- `CanLuaApplication` (`@HiltAndroidApp`) is the process initializer. It configures Firebase App Check (Debug provider in debug builds, Play Integrity otherwise), installs a custom `Configuration.Provider` to wire `HiltWorkerFactory` into WorkManager (with `WorkManagerInitializer` removed from startup via manifest merge), and on `onCreate` launches an IO-scoped coroutine that initializes `AnalyticsHelper`, `PremiumState`, `FirebaseRemoteConfigManager`, applies early-adopter premium eligibility against install time, and triggers orphan-card claiming plus immediate sync when pending work exists. Two long-lived flows observe `AuthManager.authStateFlow` (to reset guest mode and re-sync after login) and `SettingsRepository.autoSyncEnabled`/`syncOnlyWifi` (to schedule or cancel background sync).
- `MainActivity` (`@AndroidEntryPoint`, `ComponentActivity`) is the single Compose host. It keeps the native splash screen until both `InitViewModel.isDataReady` and `AuthViewModel.uiState` are resolved, gathers AdMob consent, applies locale/theme/font scale from `SettingsViewModel`, and drives a `NavHost` with four root routes: `splash`, `login`, `profile_setup`, `main?cardId={cardId}`. Deep links for `canluavn.web.app/share/{cardId}` and `canluavn.firebaseapp.com/share/{cardId}` are declared both in code (`navDeepLink`) and in `AndroidManifest.xml` (`autoVerify=true` intent-filter). The activity depends only on UI layer (`ui.screen.*`, `ui.viewmodel.*`, `ui.theme`, `ui.feedback`) and util modules; it never touches Room/Firestore directly.
Dependency direction inside this scope is strictly downward: Application → repository/util layers; Activity → ViewModel/UI layers. No cross-calls between the two except through shared repositories consumed by both.
